holdemfoldem · integration guide

Two ways into the same table.
Which one deals to your app.

backend/core.py computes one verdict. The CLI and the MCP server are just two doors into the same room — the right one depends on who's asking and from where. Below: how they actually differ, then a specific read on nuwrrrld-portal and schwab-nu1.

Compare the hand

Same engine underneath both — the difference is entirely in who's on the other end.

Dimension holdfold CLI holdemfoldem-mcp
Who calls it A person, or a shell script, at a terminal An LLM (Claude Code) mid-conversation
Transport In-process import of core.py, HTTP fallback Always HTTP, wraps a running backend
Output shape Rich terminal panel, or raw JSON with --json Compact prose summary — never the raw ~50-field payload
Success signal Exit code encodes the verdict (0/1/2/3) — scriptable Text the model reads and reasons over — no numeric contract
Best for Cron jobs, CI gates, quick manual checks, piping into other tools "What's the verdict on what I'm holding" inside a coding session
Needs running Nothing, if the local mamba env + sibling repo exist The FastAPI backend must already be up — no fallback
Wrong tool if… You're inside a web request — don't shell out from a server route You need a numeric result a program branches on
Neither is the web integration. A Next.js server route calling the FastAPI backend directly over fetch() is a third, distinct path — and it's the one your web apps should already be using.

The casefiles

What each app actually is changes which door fits — and one of them is already through it.

nuwrrrld-portal

Next.js 16 · Clerk · Neon
already correct — direct HTTP

What's already there

app/api/analyze/route.ts proxies straight to holdemfoldemapp's /api/analyze via MCP_ANALYZE_URL — server-to-server, cached, auth-gated. This is correct: a web server should never shell out to a CLI or speak stdio MCP from inside a request handler.

The gap worth closing

The portal already sends position_lots in its request schema — but nothing populates it from a real position today.

  • Confirm MCP_ANALYZE_URL is set in every deployed environment, not just local — the route 503s cleanly if it isn't, but that's still a gap worth closing before it's noticed live.
  • Where the portal has real lot data (a linked Schwab account, a manual watchlist entry), populate position_lots in the existing request instead of leaving it empty — the backend already computes P&L, aging, and cost-basis-method comparisons once it's there.
  • Leave the CLI and MCP server out of this app entirely — they add a process boundary a fetch call doesn't need.

schwab-nu1

Next.js 15 · Drizzle · read-only Schwab OAuth
bring in the MCP server

What's already there

A real FIFO lot-reconstruction engine (src/lib/schwab/lots.ts) that already produces exactly the shape PositionLot wants — qty, costBasis, acquisition date — from real Schwab transaction history. No MCP config exists yet in this repo.

Where each door fits

  • In the app itself: same pattern as the portal — a thin server route forwards a reconstructed lot to /api/analyze directly. No CLI, no MCP, for the same reason.
  • In development: this is where the MCP server earns its place. Register holdemfoldem-mcp for Claude Code sessions in this repo, and a dev debugging a lot-matching edge case can ask "what's the verdict on this position" without leaving the conversation to curl the backend.
  • For CI: the CLI's exit codes are a natural fit for a scheduled check — e.g. a nightly script that runs holdfold verdict across open positions and alerts only on FOLD EM, using the exit code rather than parsing JSON.

How it actually flows

One engine, three doors, each shaped for who's knocking.

holdfold CLI → core.compute_verdict terminal, scripts, CI — reads the exit code
holdemfoldem-mcp → FastAPI /api/analyze → core.compute_verdict Claude Code sessions — reads the prose summary
nuwrrrld-portal / schwab-nu1 → FastAPI /api/analyze → core.compute_verdict web servers — reads the JSON, renders it
